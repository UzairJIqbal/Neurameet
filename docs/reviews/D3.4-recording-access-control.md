# Review — D3.4 Recording Access Control (+ D3.4 /debug fixes)

Reviewed 2026-08-21. Scope: the D3.4 owner-only composite recording feature and the
three /debug fixes that followed (polling auto-refresh on `/recording`, the
"No tests found" config fix, and the REC-pill / new-recording visibility fix).

Runtime evidence available at review time: `tsc --noEmit` clean; the polling
regression spec `npx playwright test --project=chromium-recording-poll` passes
(2 passed, 34.9s) now that Clerk keys are present. The two-user live verify
(consent broadcast, non-owner hidden, non-owner empty `/api/recordings`) remains
BLOCKED on a second real Clerk account and a live call, so the acceptance
criteria below are reviewed against code, not against a live two-user run.

## Layer 1 — Plan alignment
**PASS, with one known open gap**

- All three acceptance criteria are implemented at the UI / listing layer:
  - Owner-only Record control: `MeetingRoom.tsx` renders the Record button only
    when `isOwner` (`call.state.createdBy?.id === user?.id`). Non-owners render
    no Record control.
  - All-participant consent: `frame_recording_started` / `frame_recording_stopped`
    drive a broadcast toast for every participant, plus a persistent REC pill in
    the top bar while `isRecording`. `frame_recording_ready` reloads the list.
  - Owner-only access afterward: `GET /api/recordings` filters
    `created_by_user_id` only; the meeting-detail Recording tab is hidden for
    non-owners (`MeetingTabs.VISIBLE_TABS`); the in-room Recordings button is
    owner-gated.
- `frame_recording.mode` is `available` (not `auto-on`) at all four
  call-settings sites (`MeetingModel.tsx` x2, `PersonalRoomPage.tsx` x2);
  `individual_recording` stays `disabled`.
- The `/debug` fixes are present and match the spec's "as built" record: bounded
  10s polling on `/recording` (90-tick ~15 min ceiling), optimistic `isRecording`
  in `handleRecordToggle`, removal of the `n > 0` early-stop in the in-room poll,
  and `EndCallButton` finalizing a running recording before `endCall()`.

**Open gap (known, per spec §10 — flagged, not newly discovered):**
Posture A's runtime `revokePermissions(START_FRAME_RECORD_CALL)` was WITHDRAWN
because the installed SDK only accepts `send-audio` / `send-video` / `screenshare`
for that call. Therefore **non-owner programmatic start of recording is NOT
server-enforced anywhere in this codebase.** The only remaining server lever is
the Stream `default` call-type role grant for `start-frame-record-call`, which is
unverified and lives outside the repo. UI gating + server-side owner-only
*listing* are in place; the deeper "a devtools user cannot start recording"
guarantee is not delivered in code. This is the open live-verify item (spec §7
step 6).

## Layer 2 — System integrity
**PASS**

- Architecture: `GET /api/recordings` owns the Stream fetch via a server-side
  `StreamClient` (secret never reaches the browser). `RecordingPage`,
  `RecordingTab`, and `MeetingRoom` are client components that only call the API
  or the Stream SDK (allowed per architecture). Owner anchor is consistent:
  client uses `call.state.createdBy?.id === Clerk userId`; server uses
  `meetings.user_id === userId` (and `meetings/[id]` is `.eq("user_id", userId)`,
  returning `user_id` at line 84).
- Design system: scan found **no raw hex and no raw Tailwind color classes** in
  the changed surfaces. Tokens used throughout (`bg-error`, `text-on-error`,
  `bg-inverse-surface`, `text-inverse-on-surface`, `bg-primary-container`, etc.).
  One minor exception: `shadow-[0_4px_20px_rgba(0,0,0,0.04)]` in `RecordingPage`
  (line 129) and `RecordingTab` (line 64) hardcodes an rgba shadow — a minor
  token violation.
- Code standards: `src/app/api/recordings/route.ts` disables
  `@typescript-eslint/no-explicit-any` and uses `any` for the call / recording
  objects (lines 45, 57). Behaviorally fine; a typed shape would be cleaner and
  matches the project's "no any" strictness. Minor.

## Layer 3 — Production readiness
**ISSUES FOUND**

- **Important — polling halts on a single failed fetch.** In `RecordingPage`
  `loadRecordings`, the `catch` block calls `clearInterval(intervalId)` and
  returns on *any* non-ok response. The entire point of the fix is to keep
  polling until a recording becomes queryable. A transient 500 from
  `/api/recordings` (or one bad tick) permanently stops auto-refresh for the rest
  of the page lifetime, so a recording that finishes later will not appear
  without a manual reload — the exact regression this fix was meant to close.
  Recommend: on error, keep polling (optionally with backoff) while still
  surfacing a toast, instead of clearing the interval.
- **Important — non-owner start gap (ties to Layer 1).** If the Stream
  `default` call type grants `start-frame-record-call` to `call_member` (the
  local Stream skill docs predict this), a non-owner can start a composite
  recording via devtools/API even though no UI button exists. Because
  `/api/recordings` is keyed to the call creator, the resulting recording shows
  under the owner's list and the non-owner's own list stays empty — so the leak
  is "a non-owner can cause the owner's call to be recorded," not "a non-owner
  sees others' recordings." Still violates the spec's stated purpose (genuine
  owner-only control) and should be confirmed or closed via the live capability
  check (spec §7 step 6) or a Stream call-type grant change.
- **Minor — noisy console.** `MeetingRoom.loadRecordings` calls
  `console.info` with the recording count on every 10s poll (up to 90 ticks).
  Noisy in production; demote to debug or remove.
- **Minor — `any` usage** in the recordings route (see Layer 2).

## Summary

4 issues found across 3 layers:
- 2 Important: polling stops on error (undermines the fix); non-owner start gap
  (known/open, depends on Stream default grant).
- 2 Minor: raw rgba shadow; `any` in the recordings route.

The plan-alignment, architecture, and design-system concerns are otherwise met.
Resolve the two Important items before moving to the next feature — in
particular the polling-on-error behavior (it directly re-opens the regression)
and the live capability check for the non-owner start gap. The two-user live
verify remains the outstanding gate for full sign-off.
